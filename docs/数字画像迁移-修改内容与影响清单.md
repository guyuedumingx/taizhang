## 1. 整体目标

将数字画像 P1（用户对齐）+ P2（业务表迁移）写进台账仓，**台账原有业务逻辑 0 改动**（除 2 处兼容性修复）。

**集成思路**（来自集成指南 §1 思路 A）：
- 数字画像代码全部进 `backend/app/portrait/` 子目录
- 业务表前缀 `portrait_`，开发 SQLite 与生产 PG/Oracle 一致
- 复用台账的 Casbin / Workflow / User 模型（其中 User 复用 taizhang users 表，不重建）
- 数字画像独有字段（is_first_login, deleted_at）走扩展表 `portrait_user_metadata`

### 批次 2：台账自身 bug 修复（`app/db/session.py`）

**变更前**：
```python
engine = create_engine(
    settings.SQLALCHEMY_DATABASE_URI,
    pool_pre_ping=True,
    pool_size=settings.DB_POOL_SIZE,
    max_overflow=settings.DB_MAX_OVERFLOW,
    pool_timeout=settings.DB_POOL_TIMEOUT,
    pool_recycle=settings.DB_POOL_RECYCLE,
    ...
)
```

**问题**：SA 1.4 + SQLite 不接受 `pool_size/max_overflow/pool_timeout` 三个参数，抛 `TypeError`，导致任何 `from app.db.session import ...` 都崩。**这是 taizhang 仓的自身 bug，迁移前根本没跑过 SQLite 模式**。

**变更后**：
```python
engine_kwargs = {
    "pool_pre_ping": True,
    "pool_recycle": settings.DB_POOL_RECYCLE,
    "echo_pool": False,
    "connect_args": connect_args if connect_args else {},
}
if settings.DATABASE_TYPE == "oracle":
    engine_kwargs["pool_size"] = settings.DB_POOL_SIZE
    engine_kwargs["max_overflow"] = settings.DB_MAX_OVERFLOW
    engine_kwargs["pool_timeout"] = settings.DB_POOL_TIMEOUT
engine = create_engine(settings.SQLALCHEMY_DATABASE_URI, **engine_kwargs)
```

**影响清单**：

| 环境 | 改动前 | 改动后 | 结论 |
|---|---|---|---|
| SQLite（开发） | import 即崩 | 正常 NullPool | **修复 bug，从不能用到可用** |
| Oracle（生产） | 传 pool_size=20, max_overflow=20, pool_timeout=30 | 同样传 | **行为完全一致** |

**影响功能**：
- ✅ SQLite 模式下整个 app 启动恢复正常（之前根本起不来）
- ✅ Oracle 生产模式行为零变化
- ⚠️ NullPool 在 SQLite 高并发下每次新建连接有微小开销 — SQLite 本就单线程场景，无影响

**回滚方式**：`git revert <此批次 commit>` 即可，恢复原状。

### 批次 3：requirements.txt 兼容性 + policy.csv 权限策略

#### 3.1 `requirements.txt`：casbin-sqlalchemy-adapter 0.6.0 → 0.5.0

**变更**：
```
-casbin-sqlalchemy-adapter==0.6.0
+casbin-sqlalchemy-adapter==0.5.0
```

**问题**：0.6.0 内部 `from sqlalchemy.orm import DeclarativeBase`（SA 2.0 API），与台账钉死的 `SQLAlchemy==1.4.50` 互不兼容。这是 taizhang 仓 requirements 自身的版本冲突。

**API 差异实测**（taizhang 实际用到的全部方法）：

| 方法 | 0.5.0 | 0.6.0 | taizhang 是否用 | 影响 |
|---|---|---|---|---|
| `add_policy` | ✅ | ✅ | ✅（role_service.py 大量） | 无 |
| `remove_policy` | ✅ | ✅ | — | 无 |
| `add_grouping_policy` | ✅ | ✅ | ✅ | 无 |
| `remove_grouping_policy` | ✅ | ✅ | ✅ | 无 |
| `remove_filtered_policy` | ✅ | ✅ | ✅（role_service.py 大量） | 无（实测通过） |
| `get_users_for_role` | ✅ | ✅ | ✅ | 无 |
| `enforce` | ✅ | ✅ | ✅（deps.py:79） | 无 |

**实测通过**：`init_casbin_rules()` + `init_permissions()` + `remove_filtered_policy()` + `enforce()` 全 OK。

**影响功能**：
- ✅ 台账现有角色管理（CRUD、权限分配、enforce 检查）行为完全一致
- ✅ 6 条 role assignment + 50+ policies 加载正常
- ⚠️ 0.5.0 是 SA 1.4 唯一可用版本 — 如果上游后续要升级 SA 2.0，需同步升 adapter

### 批次 4：数字画像业务模型（17 张表 + 1 扩展表）

**新增文件**：

| 文件 | 内容 | 表数 |
|---|---|---|
| `app/portrait/models/_base.py` | 共享常量（PORTRAIT_SCHEMA / PORTRAIT_PREFIX / beijing_now） | 0 |
| `app/portrait/models/__init__.py` | re-export 全部 19 个模型 | 0 |
| `app/portrait/models/user_metadata.py` | PortraitUserMetadata（用户扩展表，承载 is_first_login + deleted_at） | 1 |
| `app/portrait/models/profile.py` | Profile + 9 子表（political/education/family/resume/reward/qualification/achievement/language/contact） | 10 |
| `app/portrait/models/intent_project.py` | DevelopmentIntent + ProjectSummary + ProjectSummaryTag + SkillTagTemplate + ProfileSkillTag | 5 |
| `app/portrait/models/log_visit_transfer.py` | OperationLog + HomeVisitRecord + GroupTransferHistory | 3 |

**总计 19 张表**（含 1 张 P1 扩展表）。

**表名规范**：

| 类别 | 命名 | 示例 |
|---|---|---|
| portrait 业务表 | `portrait_` 前缀 | `portrait_profiles`、`portrait_home_visit_records` |
| portrait 用户扩展表 | `portrait_` 前缀 | `portrait_user_metadata` |
| taizhang 原表 | 不动 | `users`、`teams`、`roles` |

**外键策略**：
- portrait 表之间 FK 全部走 `portrait_xxx.id`
- portrait 表 → taizhang users 表（`portrait_profiles.user_id → users.id`、`portrait_user_metadata.user_id → users.id` 等）
- **不创建** taizhang 表 → portrait 表的外键（避免 taizhang 原表被迫感知 portrait 存在）

**与原集成指南的差异**：

| 项 | 原计划 | 实际决策 | 原因 |
|---|---|---|---|
| Schema 隔离 | `schema="digital_portrait"` | 改用 `portrait_` 表名前缀 | SA 2.0 + SQLite 不能 resolve 跨 schema FK，SA 1.4 在 SQLite 下行为不稳定 |
| FK 写法 | 跨 schema | 全部同 schema 内 | 表名前缀方案无需跨 schema，部署由 DBA 在生产环境 schema 内建 portrait_xxx 表 |

**实测验证**：SA 1.4 + SQLite + portrait_ 前缀方案，create_all 0 错误，19 张表全部建好。

**影响台账现有功能**：**零**。新建表全部在 taizhang DB 内新增，不修改任何 taizhang 原表的列、约束、索引。

**回滚方式**：删除 `app/portrait/models/` 整个目录 + `DROP TABLE portrait_*` 即可（独立命名空间，回滚干净）。

### 批次 5：数据迁移脚本（`backend/migrate_portrait_p1.py`）

**功能**：把 digital_portrait SQLite 的 `users` 表导入到 taizhang `users` + `portrait_user_metadata` 扩展表。

**字段映射规则**：

| 源（digital_portrait） | 目标（taizhang） | 处理 |
|---|---|---|
| `ehr_no` (String(50)) | `ehr_id` (String(7)) | 7 位数字硬校验，否则跳过 |
| `name` | `name` | 直接映射 |
| `group_name` | `department` | 直接映射 |
| `password_hash` (PBKDF2) | `hashed_password` (bcrypt) | 一致占位 hash + is_first_login=True 强制改密 |
| `is_disabled` | `is_active` | **语义反转**：True → False |
| `is_superadmin` | `is_superuser` | 直接映射 |
| `is_first_login` | `portrait_user_metadata.is_first_login` | 移到扩展表 |
| `deleted_at` | `portrait_user_metadata.deleted_at` | 移到扩展表 |
| `role` | （废弃） | 走 Casbin，不复制 |
| `id` | `users.id` (新) | 新建自增 ID |

**特性**：
- ✅ 支持 `--dry-run`（只打印计划）
- ✅ 显式报告 `created / skipped / errors` 三项计数（Rule 12）
- ✅ 失败行不中断，跳过并记录原因
- ✅ dry-run 通过：源 19 条数据 100% 因 ehr_no 不符 7 位数字被跳过（属于数据层问题）
- ✅ 结论：源数据是测试假数据，台账自有 3 个真实用户（id=1/2/3）全部合规，无需 LIVE 迁移

**影响台账现有功能**：**零**。脚本是独立的一次性工具，跑完后可保留作为审计工具但不主动运行。

**回滚方式**：直接删除该脚本文件即可。已 LIVE 跑过的话，用 DB 快照回滚。

特性：
- ✅ `--dry-run`：只打印计划

- ✅ 依赖前置：需要先跑 init_db 创建 admin role（或手动 insert）

**实测**：
- 4 套模板创建成功，id=4/5/6/7，每个 3 节点（start/approval/end）
- 审批节点 approver_role_id=3 指向 admin role

**集成指南 §5 雷区合规**：
- 1. 不改 Casbin rbac_model.conf ✅（policy.csv 已配）
- 2. 不 DROP workflow instances ✅（--reset 只删模板，不动实例）
- 3. 不塞 portrait 字段进 ledger.data ✅
- 4. 不跨 schema 事务 ✅

- 6. 不改 ApprovalStatus 枚举 ✅

**影响台账现有功能**：**零**。新建模板走 taizhang 现有 WorkflowService（crud_workflow.py），不修改任何台账代码。

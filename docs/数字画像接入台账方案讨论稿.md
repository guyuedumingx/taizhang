## 0. 文档目的

数字员工画像项目（`D:\code\digital_portrait`）近期需求发生重大变化，从静态档案扩展到包含审批流的动态数据（专项工作、活动报名、家访维护、批量导入）。同时考虑到资产管理系统、台账系统未来也可能需要接入，**我们需要在"接入台账统一基础设施"和"独立演进"之间做选择**。

本文档对比两套方案，给出推荐与依据，供团队讨论决策。

---

## 1. 背景与目标

### 1.1 当前状况

| 项目 | 代码位置 | 用户管理 | 审批引擎 | 动态字段 | 数据库 |
|---|---|---|---|---|---|
| 数字员工画像 | `D:\code\digital_portrait` | 自己管（PBKDF2 哈希）| ❌ 无通用引擎 | ❌ 无 | SQLite（计划迁 Oracle） |
| 台账系统 | `D:\code\taizhang` | ✅ Casbin RBAC | ✅ 4 级 Workflow 抽象 | ✅ Template+Field | PostgreSQL/Oracle |
| 固定资产 | `D:\code\gudingzichan01` | 自己管（PBKDF2）| ❌ 无 | ❌ 无 | SQLite |

### 1.2 待解决的核心问题

1. **数字画像新需求**（动态表单 + 审批流 + 批量导入 + 展示导出）需要基础设施支持
2. **三系统用户表分散**：用户改一次密码要三个系统都改
3. **三系统审批/字段机制各自造轮子**

### 1.3 决策时间窗口

数字画像新需求等待方案确定后启动。**当前可承受的延迟：1-2 周**（不紧迫，但不能无限期搁置）。

## 2. 两套方案

### 方案 A：写入台账（数字画像作为台账的业务模块）

**核心做法**：把数字画像代码作为台账项目的一个子目录，**复用台账的用户管理、Casbin 权限、Workflow 审批引擎、Template/Field 动态字段机制**。

```
D:\code\taizhang\
├── backend/app/portrait/        ← 数字画像作为子模块
│   ├── routers/                 ← /api/v1/portrait/*
│   ├── services/                ← 数字画像业务逻辑
│   └── models/                  ← 数字画像业务表（独立 schema）
├── frontend/src/pages/portrait/ ← 数字画像页面
└── docs/
```

### 方案 B：现有数字画像项目基础上改造（独立演进）

**核心做法**：不动台账，**在数字画像项目里把台账已有的基础设施全部重建一遍**。

```
D:\code\digital_portrait\
├── backend/app/
│   ├── workflow/                ← 新增：自建审批引擎
│   ├── dynamic_form/            ← 新增：自建动态字段
│   ├── rbac/                    ← 新增：自建权限
│   ├── auto_fill/               ← 新增：自动填充
│   └── export/                  ← 增强：导出
└── frontend/src/components/
    └── ...（新增：动态表单/审批 UI）
```

## 6. 推荐与依据

### 6.1 我们的推荐：**方案 A（写入台账）**

**推荐依据**：

1. **测试覆盖充足**（已验证）→ 改台账代码风险可控
2. **新需求几乎都需要审批** → 台账 Workflow 现成
3. **新需求几乎都需要动态字段** → 台账 Template/Field 现成
4. **资产将来也要接入** → 共享基础设施收益最大
5. **台账是我们开发的** → 技术债可控，不是黑盒
6. **代码量少 50%** → 同样的事不用写两遍

### 6.2 何时应该选 B

| 触发条件 | 为什么选 B |
|---|---|
| 数字画像要作为**独立产品卖给外单位** | A 让数字画像变成台账附属 |
| **数字画像 + 资产系统都要物理独立部署** | A 共享数据库不适合 |
| 团队**有人精通 SpiffWorkflow 等开源引擎** | B 的引擎开发成本降低 |
| **绝对不能让数字画像受台账变更影响** | B 完全隔离 |

### 6.3 决策树

```
问：将来数字画像要独立出去/卖给外单位吗？
│
├─ 是 → 选 B
│
└─ 否（中行内部使用）
    │
    ├─ 资产系统也要接入吗？
    │   ├─ 是 → 选 A（统一基础设施）
    │   └─ 否 → 选 A 或 B 均可，看团队偏好
    │
    └─ 想要"一个入口管所有" vs "数字画像自己说了算"？
        ├─ 统一入口 → A
        └─ 自主可控 → B
```

## 8. 待讨论问题

请同事在阅读本文档后，重点讨论以下问题：

### 8.1 业务边界问题

1. **"账务系统里出现家访/技能"是否可接受？**
   - 选项 1：台账升级为"内网统一工作平台"，账务只是其中一个模块 → 选 A
   - 选项 2：台账就是台账，业务严格隔离 → 选 B

2. **数字画像业务表是否进台账库？**
   - 选项 1：进台账库独立 schema（`digital_portrait`） → A
   - 选项 2：数字画像保持独立数据库 → B

3. **数字画像是否要支持未来独立推广？**
   - 是 → 选 B
   - 否 → 选 A

### 8.2 技术问题

4. **哈希算法冲突如何解决？**
   - 选项 1：统一改 bcrypt（推荐）
   - 选项 2：统一改 PBKDF2
   - 选项 3：并存识别

5. **数字画像的 role 字段如何处理？**
   - 选项 1：废弃，改用台账 Casbin RBAC
   - 选项 2：保留 role 字段作为 Casbin 同步缓存

6. **`is_active` vs `is_disabled` 语义反转如何对齐？**
   - 选项 1：选 `is_active` 为标准（推荐）
   - 选项 2：保留 `is_disabled`，加 property 兼容

### 8.3 责任问题

7. **改台账代码后，账务功能出 bug 谁负责？**
   - 选项 1：谁改谁负责（建议写书面记录）
   - 选项 2：成立代码 review 小组

8. **数字画像模块的代码维护谁负责？**
   - 选项 1：数字画像开发独立维护
   - 选项 2：台账开发负责 review，数字画像开发负责实现

### 8.4 时间问题

9. **新需求的交付时间预期？**（虽然说不卡工期，但同事应该知道期望）

10. **灰度发布的策略？**（P5 阶段的 10% → 50% → 100%）

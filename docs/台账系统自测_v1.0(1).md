# 第一部分答案

## A1 参考答案

**选 B。**

A「数据库表」是技术实现；C「用户别名」无关；D「审批节点」是工作流概念。**台账是业务对象**，在不同业务里指不同的事物（银行流水、人事档案、库存记录），但本质都是"需要被系统记录和追踪的一条条数据"。

---

## A2 参考答案

**选 B。**

台账是**静态数据**，工作流是**数据被处理时的动态过程**。例如一笔台账（"采购订单"）：它本身是数据，但它有「提交→部门审批→财务审批→生效」的流程。一笔台账在没有工作流时也是台账；一段工作流没有台账数据也无意义。

---

## B1 参考答案

合理项（任列 5-6 项）：

- **找数据**：关键词搜索、高级筛选（按时间/创建人/状态）、排序
- **看数据**：分页、详情页跳转、单条数据预览
- **操作数据**：批量操作（删除/导出）、单条编辑/删除按钮
- **辅助**：导出（全部/筛选后导出）、列自定义、列宽

---

## B2 参考答案

**先做搜索**。

10 万条不分页用户根本看不到数据（全量渲染会卡死）。但**先做搜索**是因为：用户进来找数据是核心场景，找不到再快也没意义。如果产品定位是"管理后台、用户精确查找"，搜索是 P0；如果定位是"浏览、翻页"，才考虑分页优先。

---

## C1 参考答案

**选 C（草稿、活跃、已完成、已退回）。**

A 是抽象方法论；B 「进行中」语义模糊（处于哪个阶段？）；D 是 CRUD 操作不是状态；**C 是最经典的台账生命周期**：用户起草→提交后变活跃→审批通过/正常结束变已完成→被退回到草稿。退回是常见的审批反向流程。

---

## C2 参考答案

**选 B。**

已完成状态意味着数据已经走完了所有流程（审批通过/业务结束），此时改数据会：
1. 破坏"已存档"的可信度（事后改账谁负责？）
2. 与下游系统对账时不一致
3. 审计/合规风险

所以通常是"想改就新建一条冲账"，而不是直接改已完成。

---

## D1 参考答案

合理要点（任答 2 个即可）：

1. **权责分离**：避免一个人说了算——单据要走上级/财务/合规复核才生效
2. **流程规范**：把"谁审、审什么、什么条件下通过"沉淀成可追溯的规则
3. **风险控制**：金额超限/敏感操作必须多人把关
4. **可追溯**：审批通过后留下"谁在何时批的"证据，出问题可倒查

---

## E1 参考答案

**选 A（防止误操作 + 权责分离）。**

权限系统的核心目的就是这两个：① 防止小白误删生产数据；② 让"谁能看/改什么"和岗位职责对齐（财务只能管账，HR 只能管人）。B 性能、C UI 都不是根本原因；D 显然不对。

---

## E2 参考答案

合理定义：把"谁能看见哪些台账"按**所属团队**做隔离。组长只看本组，部门长看本部门，超管看全部。

为什么要做：
1. **数据安全**：HR 的薪酬台账不能让一线员工看到
2. **工作聚焦**：每个用户只看到和自己有关的台账，不被海量无关数据淹没
3. **合规**：跨团队的数据隔离是很多行业的硬性要求（如金融、医疗）

---

## F1 参考答案

最少 5 件事：

1. **入口**：列表页加"批量选择"复选框 + "批量删除"按钮（仅当勾选的都是自己创建的草稿时按钮才可用）
2. **后端接口**：`POST /ledgers/batch-delete` 接收 ID 列表，返回成功/失败明细
4. **状态过滤**：接口必须二次校验每条都是「草稿 + created_by_id == 当前用户」——前端过滤不可信，后端是底线
5. **权限校验**：调用 `deps.get_current_active_user` 拿到当前用户 ID，逐条比对 `created_by_id`
6. **操作反馈**：成功后刷新列表 + 提示"成功删除 N 条，失败 M 条（原因：草稿已被他人编辑等）"，失败明细可点击查看

# 第二部分答案

## Q1 参考答案

合理步骤拆分（任选 4-6 步即可）：

1. **读取文件**：输入 HTTP 上传的二进制流，输出内存 bytes
2. **解析 Excel**：输入 bytes，输出 `headers: list[str]` + `rows: list[dict]`
3. **校验每行**：输入单行 dict，输出该行的问题列表 + 是否可导入
4. **检测重复**：输入所有行 + 已有台账，输出每行的重复标记
5. **汇总报告**：输入所有行的结果，输出校验报告（总数、可导入数、问题行数、明细）
6. **写入数据库**：输入可导入的行 + 报告，输出新建的台账 ID 列表 + 失败明细

**评分要点**：
- A 档：5-6 步，每步都有"做什么+输入+输出"
- B 档：步骤不全或粒度太粗（混在一起）
- C 档：列不出几个步骤

## Q2 参考答案

校验报告最少要包含：

1. **总行数**（Excel 数据行总共多少条）
2. **可导入数**（校验通过的多少条）

## Q3 参考答案

> 题目问的是「存储**结构**」——主体是 `ledgers` 表（`backend/app/models/ledger.py`），但完整答案不止一张表，配套表见下方。核心设计思想：**ledger 是通用容器**——业务字段的值不做成固定列（不是"流水号/金额/柜员号"各一列），而是整体存进 `data` JSON，字段结构由模板决定，所以这张表什么业务都能装、加新台账类型不用改表。

| 分组 | 字段名 | 类型 | 必填 | 作用 |
|---|---|---|---|---|
| 基本信息 | `id` | int, 主键 | 是 | 行唯一标识，一切外键/操作/审批记录都指向它 |
| | `name` | str | 是 | 台账名，列表显示与检索用（加索引） |
| | `description` | text | 否 | 备注 |
| 业务字段 | `data` | json | 否* | 模板定义的字段值整体存这里（流水号/金额/柜员号…），模板变了表结构不用变 |
| | `template_id` | int, FK→templates | 否* | 这条台账由哪个模板生成：决定有哪些字段、走哪套工作流 |
| | `team_id` | int, FK→teams | 否 | 归属团队，"团队可见性"隔离的依据 |
| 人的字段 | `created_by_id` | int, FK→users | 是 | 业务归属：导入场景下 = 按柜员号反查到的"这条账是谁的" |
| | `updated_by_id` | int, FK→users | 是 | 最后修改人，审计追溯 |
| | `current_approver_id` | int, FK→users | 否 | 当前停在哪个审批人手里，驱动审批流转 |
| | `imported_by_id` | int, FK→users | 否 | 实际执行导入操作的人；与 `created_by_id` 区分（操作者 ≠ 业务归属） |
| 导入扩展 | `import_batch_id` | str(40) | 否 | 导入批次号（UUID，加索引）：按批次反查、审计追溯、未来支持整批撤回 |
| 状态字段 | `status` | str | 是 | 生命周期（draft/active/completed），默认 draft |
| | `approval_status` | str | 是 | 审批状态（pending/approved/rejected），默认 pending；与 status 分开——"活着没有"和"批没批"是两个维度 |
| 时间字段 | `created_at` | datetime | 是 | 创建时间（库默认 now()） |
| | `updated_at` | datetime | 否 | 更新时间（onupdate 自动刷新） |
| | `submitted_at` | datetime | 否 | 提交进审批的时间 |
| | `approved_at` | datetime | 否 | 最终审批通过的时间 |

\* 库层面允许为空（历史原因：早期手工创建可以不带模板）；业务上**导入**产生的台账必然有 `template_id` 和 `data`。

**配套表（"存储结构"的其余部分）**：

| 表 | 作用 | 真实系统的取法 |
|---|---|---|
| `templates` + `fields` | 模板表：定义一种台账有哪些字段、走哪套工作流——`data` JSON 的"schema" | 有（模板 + 字段表，逐字段一行） |
| `ledgers` | 主体：一行 = 一条台账，业务值在 `data` | 有，即上表 |
| 导入批次表 | 一次导入一行：总数 / 成功数 / 失败数（对应 Q2 的报告数字） | **没建**：批次元信息记在 `system_logs`，计数按 `import_batch_id` 从 `ledgers` 聚合 |
| 导入错误明细表 | 行号 + 字段 + 原因 + 原始值（对应 Q8 的展示要素） | **没建**（简化）：只在导入响应和失败 xlsx 里返回，不入库 |
| `system_logs` | 操作留痕（谁、何时、IP、动作） | 有 |

「要不要单独建批次表 / 错误表」本身就是设计权衡：建表清晰可查但多一次写入；不建省存储但查询靠聚合。两种都对，能说出取舍就是好答案。

**评分要点**：
- A 档：8 个以上字段，分组清晰，覆盖 主键 / name / `data` JSON / 模板外键 / 两个状态 / 创建人 / 时间；能说出 `created_by_id` 与 `imported_by_id` 的区别是亮点
- **加分项**：设计出配套表（模板表 / 导入批次表 / 错误明细表 / 日志表）——题目问的是"存储结构"，多表在射程内；错误明细表对上 Q8、批次表对上 Q2，说明 Part 2 打通了
- B 档：5-8 个字段，或漏掉状态、时间、审计类字段
- C 档：少于 5 个，或把表设计成"流水号/金额/柜员号"这类固定业务列——没理解 ledger 是通用容器，业务值应该进 `data`

## Q4 参考答案

**选 C（已批准/已完成）**。

**理由**：导入走的是 Excel，已是人工事先校验过的数据；再走审批流没有意义（Excel 就是"批"）。导入即生效，节省流程。但具体值可以是 `completed + approved` 对齐审批通过终态。

A/B 都意味着还要再走一道流程，不合理。D 不设状态会让"导入数据 vs 手工数据"无差别，无法区分。

## Q6 参考答案

**选 A（1 条：一行就是一行的问题）**。

**理由**：业务上用户关心的是"有几行要改"，不是"有几十个单元格要改"。前者直接对应"我要回去改 Excel 的哪几行"，后者只是装饰性的细节。一行多错必须按行去重，否则用户看到"问题 10 条"会以为是 10 行要改，体验割裂。

## Q7 参考答案

**选 A（要发现）**。

**理由**：流水号是唯一标识，如果文件内就有重，导入后数据库会有冲突（取决于有没有索引兜底，但即便数据库允许，业务上也是错的）。这种错误**前置拦截**比入库后再清理成本低得多。

## Q8 参考答案

合理方案（任答出 3 点里的 2-3 点即可）：

1. **整体结构**：**按行分组**列出，每组内平铺该行的所有错误明细。**不要**按错误类型分组（用户改 Excel 时按行改，按类型分组让用户跨 Tab 跳来跳去）。
2. **每行内容**：行号 + 该行有几个错 + 每条错误的"字段名 + 原因 + 原始值"
3. **找格子**：行号 + 字段名 + 原始值，让用户能直接定位到 Excel 第几行第几列要改

**反例**：
- ❌ 按"必填缺失/团队不存在/柜员号不存在"分 Tab
- ❌ 只显示行号，不显示字段名
- ❌ 把 raw 隐藏（用户不知道原值是什么）

**评分要点**：A 档能想到"按行分组、平铺字段错误"；B 档提到分组但没说细节；C 档只说"用表格展示"

## Q9 参考答案

1. **10000 行**：**阻止**，超硬上限直接报错让用户拆文件。理由：单文件过大可能拖垮服务/超时，且大概率是用户导错了。
2. **未知列**：**忽略 + 提示**，不影响校验但告诉用户"你填了模板外的列，会被丢弃"。理由：不阻塞合法数据导入，但要让用户知道。
3. **必填为空**：**阻止该行导入**，其它合法行继续。理由：单行级问题不应影响整批。

## Q10 参考答案

```python
def check_required(row, required_fields):
    missing = []
    for f in required_fields:
        v = row.get(f)
        if v is None or (isinstance(v, str) and v.strip() == ""):
            missing.append(f)
    return missing
```

**评分要点**：
- A 档：5-8 行能跑，覆盖 None / 空串 / 缺键（注意 strip 处理全空格字符串）
- B 档：有漏洞（如没考虑空串 `""`，或没处理 key 不存在的 `KeyError`）
- C 档：写不出或交白卷

# 数字画像并入台账 · P4 前端界面设计方案

日期：2026-09-20
状态：视觉基准、重复页面策略、导航信息架构均已定稿（2026-09-20 拍板）

**已拍板：导航采用方案 B（纯菜单平铺）**——不建门户首页，"数字画像"分组下菜单直达功能页。

## 一、已确认的设计决策

| 决策项 | 结论 |
|---|---|
| 视觉基准 | **台账壳 + 画像组件语言**：侧边栏/面包屑/白色圆角内容容器沿用台账现有规范（存量页面不动）；画像页面内部用画像的组件语言（筛选栏、角色徽章、彩色技能标签、档案卡片流、预警卡、图表配色） |
| 重复页面 | **收编合并**：用户管理/操作日志用台账现有页面扩展画像字段（组别、画像角色、应急先锋队、首登强改）；修改密码走台账个人中心。画像不再保留独立入口，保证单一事实源 |
| 主题色 | 两系统同为珊瑚红 #D05A6E，无冲突 |

## 二、待拍板：导航信息架构（方案 A vs B）

两个可交互 demo（浏览器直接打开，点左侧菜单/卡片可切换页面）：

- **方案 A · 画像门户工作台**：[p4-ui-demo-A-portal.html](./p4-ui-demo-A-portal.html)
  "数字画像"分组下含**画像首页**（彩色图标卡片门户，保留画像原 Home 体验），点击卡片或菜单进入功能页。
- **方案 B · 纯菜单平铺**：[p4-ui-demo-B-flat.html](./p4-ui-demo-B-flat.html)
  无门户页，"数字画像"分组下 8 个菜单项直达功能页，菜单更短。

> 两个 demo 的页面内部（我的档案卡片流 / 档案管理列表 / 能力分析预警+图表）完全相同——差异仅在导航层与是否有门户首页。

### 权衡表

| 维度 | A 门户工作台 | B 纯菜单平铺 |
|---|---|---|
| 新用户引导 | 强：门户卡片即功能入口，与画像原版体验一致 | 弱：只看菜单名猜功能 |
| 菜单长度 | 分组下多一项"画像首页" | 最短 |
| 老用户效率 | 进画像功能多一次门户中转（可从侧边栏直达，实际无损） | 直达 |
| 开发成本 | 多做一个门户页（复用画像 Home.jsx 改造，约 0.5-1 人日） | 省这一个页面 |
| 品牌感/产品感 | "数字画像"是一个完整产品的心智 | 画像降级为一组功能页 |
| 将来扩展 | 门户可放统计摘要/待办（如"待我审批的家访"） | 无承载面 |

**建议：方案 A**。多花约 1 人日换来引导性和产品感，且门户首页将来可承载"待办审批/组内动态"等聚合信息；老用户可绕过门户从侧边栏直达，门户不构成效率损失。

## 四、画像组件语言规范（开发参照）

- 主色 `#D05A6E`（hover `#BA4A5B` / active `#A03D48`），选中态浅红底 `#F6E7EA`
- 白卡：圆角 8px、边框 `#e8e8e8` 或浅阴影 `0 1px 4px rgba(0,0,0,.05)`；页面灰底 `#f5f5f5`
- 页头模式：`标题(18px) + 灰色副标题说明句(13px #8c8c8c)`
- 筛选栏：一行排列、图标前缀输入框、珊瑚红查询按钮
- 角色徽章：圆角胶囊描边（管理员浅红底）、技能标签：pastel 彩底（绿/紫/蓝/橙）
- 档案卡片流：每模块一张白卡（标题+分隔线+展示网格+虚线新增按钮），右侧珊瑚红悬浮锚点导航
- 分析页：蓝色信息条（规则说明）→ 风险预警卡（红/黄/绿计数+灰底行）→ 双列图表卡（蓝/珊瑚红柱色）

## 五、实施注意事项

1. **技术形态**：画像前端是 JSX（无 TS），台账是 React+TS。并入时逐页移植为 TSX，类型按台账 types.ts 约定补齐；API 层走台账 services 封装（带 token 的同一 axios 实例），不走画像原 api.js。
2. **角色语义**：画像的 leader 本组数据范围依赖"组"，并入后组别取自用户扩展表（portrait_user_metadata / 台账 team 的映射需在 P4 后端定案）。
3. **审批入口**：画像 4 类审批提交后接台账 workflow_instances，审批人从台账"审批任务"页处理，画像侧不重建审批收件箱。
4. **首登强改**：画像的 is_first_login（扩展表）并入后挂到台账登录后跳转逻辑，复用台账修改密码页。

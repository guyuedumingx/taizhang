## 2. echo 与 session.py（crypto 不动，已确认 echo 无影响）

`session.py` 的 `echo=True` **只在 SQLite 分支**；内网走 else 分支（Oracle），那里只有 `echo_pool=False`——**对内网 Oracle 完全没有影响**。可以删掉（省得本地 SQLite 调试刷屏），不删也无碍。

顺带发现两个真问题（建议一并修）：

1. Oracle 分支 `max_overflow = settings.DB_POOL_SIZE` —— **应为 `DB_MAX_OVERFLOW`**。现在溢出上限被错设成池大小（5），突发并发时比设计值少一半弹性。
2. `config.py` 里 `DB_POOL_SIZE`/`DB_MAX_OVERFLOW` 定义了两次（56-57 行与 99-100 行，后者生效）+ 112 行残留 `print(settings.DB_POOL_SIZE)`。无害，清理一次即可。

## 3. alembic 两套体系：不换、不合、不混

- **外网根目录 `/alembic/`**：4 个版本（email×2、default_workflow、merge_heads），项目早期遗留。这个项目实际建表一直走 `init_db.py` 的 `create_all`，这套 alembic **从未真正管过库**。
- **内网 `backend/alembic/`**：你们自己生成的版本链，管理内网 Oracle 真实结构，`alembic_version` 表记录的是这条链的 revision id。

两条链的 revision id 完全不同，**混用会让 alembic_version 错乱**。结论：内网把自己的 `backend/alembic` 当唯一权威继续用；外网根目录那套视作死代码（可在合并时直接丢弃，绝不要拷进内网）。**你不需要为此改任何代码。**

## 5. import_batch_id 标识符无效：根因与修复

**根因**：内网模型带着 `imported_by_id`/`import_batch_id`（来自 10-26 外网包的导入 V2 功能），但内网 alembic 版本链**没有**这两列。已逐版本核对：`ehr_id`、`approval_status`、`field_value`、`last_password_change`、`approver_actions`、`default_fields` 都有迁移覆盖，**唯独缺这两个**。SQLAlchemy 查 `taizhang_ledgers` 时会 SELECT 全部映射列 → ORA-00904。

导入功能"内网没有"只是菜单/权限没启用——**代码和路由都在**（`api.py:11` 注册了 `ledgers_import`）。补列后即使不用导入也不会再报错。

**在 Oracle 执行**（⚠️ 不要照抄 `migrate_ledger_import_fields.py` 打印的 DDL——它写的是无前缀的 `ledgers`/`users`，与内网表名不符）：

```sql
ALTER TABLE taizhang_ledgers ADD (imported_by_id NUMBER);
ALTER TABLE taizhang_ledgers ADD (import_batch_id VARCHAR2(40));
CREATE INDEX ix_taizhang_ledgers_import_batch_id ON taizhang_ledgers(import_batch_id);
-- 可选外键（与模型定义对齐）：
ALTER TABLE taizhang_ledgers ADD CONSTRAINT fk_taizhang_ledg_imported_by
  FOREIGN KEY (imported_by_id) REFERENCES taizhang_users(id);
```

执行后重启后端，台账列表/详情应立即恢复正常。

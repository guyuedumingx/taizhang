## 🔴 阻塞项（必须现在拍板）

### 决策 1 · 组长以什么标识为准？

**现状**：代码里"组长 ≡ `users.team_id` 非空"（在哪个组就是组长）。
**后果**：任何员工只要被分了个组，自动获得组长权限——能看本组所有人档案、能建家访、能审批。

**真实组长标记其实存在，但一次都没用过**：`teams.leader_id`（`app/models/team.py:15`）。
**角色系统也存在但没用过**：`roles` 表存在，画像模块从不引用 casbin。

| 选项 | 做法 | 工作量 | 风险 |
|---|---|---|---|
| **A** | 启用 `teams.leader_id` | 小（8 处 service 改判据） | 需处理历史数据：一组多人谁是组长 |
| **B** | `users` 表加 `is_team_leader` 字段 | 中（加字段 + 迁移 + 管理界面） | 最直白，但破坏"台账 0 改动" |
| **C** | 启用 casbin `manager` 角色 | 中（与台账用户管理对齐） | casbin 现有 manager 语义比 PRD 宽，需收口 |

> **配套建议**：选 A 或 B 后，需同步修正测试里的"普通员工"定义——当前测试用 `team_id=None` 代表普通员工，一旦组长判定改变，这些用例会集体失效。

**影响面**：审计报告 §1.1 列了 8 项功能会因此改变行为（他人档案查看、档案管理列表、家访新建、家访列表、出入境台账、消防演练）。

### 决策 2 · 画像单独部署后，员工账号从哪来？

**已确定**：画像将来在内网**单独装一套**，不与台账共用数据库。

**未定**：导入模板有几列、初始密码怎么发。

PRD 全文关于员工导入只有一句话（`:581`）：「EHR 必填、姓名/组别必填」，**没有完整列定义**。另有一处提到换组模板是 `EHR、新组别、原因`（`:475`），那是换组不是建号。

需要拍板的：

| 待定项 | 说明 | 建议默认 |
|---|---|---|
| 必填列 | EHR 号、姓名、组别（+ 岗位？部门？） | 沿用 3 列 |
| 可选列 | 岗位 / 部门 / 手机 / 入职日期 | 按需 |
| 初始密码 | 统一初始密码？还是每人随机生成后导出？ | 统一 + 强制首登改密（`is_first_login` 已实现） |

| 停用/离职 | 导入时如何处理已存在但已停用的人 | 需拍板 |

> **注意**：`portrait_user_metadata.is_first_login`（首登强制改密）字段和逻辑**已经实现**（`auth_service.py:23`），初始密码方案可以直接复用它。

### 决策 6 · "修改档案"这个提交类型还要不要？

**现状**：员工提交档案修改 → 管理员点通过 → **档案不会变**。
`submission_service.py` 文件头自述「profile_edit : 暂不应用 field 改动 (P5+ 接入)」，`approve()` 里只有专项工作和活动申报两个分支，没有档案修改。

- **A. 废弃**——下掉该提交类型，写进 PRD 变更记录（曾有 2026-10-10 "改为管理员直改"的决定，但没进 PRD）
- **B. 补联动**——在 `approve()` 里实现字段写回

### 决策 7 · 删除用户：软删还是砍硬删？

- PRD §17.3 要求软删（`deleted_at`），实际是 `db.delete()` **硬删**
- SQLite 的外键约束是**关闭的** → 误删直接产生孤儿数据
- 且"禁用"（`is_active`）已实现且语义重叠

- **A. 只留禁用**——砍掉硬删按钮
- **B. 真软删**——引入 `deleted_at`，保留可恢复

> **现状补充**：`portrait_user_metadata.deleted_at` 字段已存在，但**没有任何代码按它过滤**。`home_visit_service.py:143` 有个 `hasattr(models.User, "deleted_at")` 守卫，而 `User` 根本没这列，该分支恒为真——等于没写。软删要做就得从头做。

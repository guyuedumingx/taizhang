### 决策 1 · 组长以什么标识为准？→ **A：启用 `teams.leader_id`**

**要解决什么**：代码里"组长 ≡ `users.team_id` 非空"——**任何员工只要被分了个组，就自动获得组长权限**（能看本组所有人档案、能建家访、能审批）。这是审计报告 §1.1 里 8 项功能权限过宽的共同根因。

**已存在的字段**：`teams.leader_id`（`app/models/team.py:15`，`ForeignKey("users.id")`），建表时就有，**代码里一次都没用过**，当前全是 NULL。

**做法**：
- 组长判据从 `viewer.team_id is not None` 改成 `viewer.id == team.leader_id`
- 组表里的 `leader_id` 指向本组的某个人；谁被指向谁是组长
- 一组一个组长，组长身份跟着他所在的组走

##### 怎么判断台账域那 8 处该不该跟着改（2026-10-21 补充判断方法）

先分清**两套语义**的差别，这是判断的前提：

| | 画像的「组长」 | 台账的「同组」 |
|---|---|---|
| 谁能用 | 组长 1 个人（`teams.leader_id` 指向的那位） | 全组所有人（`team_id` 相同的都算） |
| 业务含义 | 「这个组的负责人」，有管理动作（建家访、审批、看本组全员档案） | 「这份台账属于我们组」，组内成员都能看/提交 |
| 判定式 | `viewer.id == team.leader_id` | `viewer.team_id == record.team_id` |

**判断口诀：这条权限的**受益人**是"一个人"还是"一群人"？**

- 受益人是**一群人**（组内成员共同查看/提交本组数据）→ 保留「同组」语义，**不要**改成组长判据。
  - 台账 8 处基本都属于这一类：台账是"组的台账"，组员都要能录能看。
- 受益人是**一个人**（某个角色专属的管理动作，如"审批人必须是组长"）→ 应统一到 `teams.leader_id`。

**具体到本项目，判断步骤**：

1. 先确认**业务上到底谁该有这个权限**，而不是先看代码怎么写的。问业务方一句："这项操作，组里的所有人都能做，还是只有组长能做？"
2. 若答案是"只有组长" → 换成 `TeamService.is_leader(db, user)`。
3. 若答案是"组里都行" → 保留同组语义，**但要在代码里写清注释**，标明"这是台账的同组语义，不是画像的组长语义"，避免下次又被当成待统一的漏洞。
4. 换判据时注意**存量影响**：台账域现在有 174 人已分组、10 个组的 `leader_id` **全是 NULL**（决策 1 历史数据一节），若贸然把台账域也改成组长判据，**这 174 人会立刻失去台账权限**（且比画像侧更严重——台账是日常主流程）。所以台账域统一判据**必须等组长指定做完之后**再做。

> **结论（当前不动）**：画像域 21 处已全部收口到 `is_leader`；台账域 8 处保持"同组"（业务上正确）；`approvals.py:409-412` 的 500 死代码**已按方案 C 修复**（撤回仅限创建人 + 超管，见上一节）。

##### ✅ 架构张力：已拍板 → **形态 B：一个仓库 + 一个应用 + 两个数据库文件**（2026-10-21）

> ⚠️ **编号说明**：本节原先的「三选一」（A 搬表 / B 共库 / C 共库+代码隔离）已被**另一套编号**取代。下文用 **形态 A / 形态 B / 形态 C** 指代新方案，**与旧编号不对应**，别混。

**决策内容（一句话）**：画像**不拆成独立项目**，仍是同一个仓库、同一个 FastAPI 应用、同一套登录；但**数据落到两个独立的数据库文件**（`taizhang.db` + `portrait.db`），`users` / `teams` 两张表**共用**。

| 维度 | 形态 A 保持现状 | **形态 B ✅ 已选** | 形态 C 独立项目 |
|---|---|---|---|
| 仓库 | 同一个 | **同一个** ✅ | 拆成两个 |
| 应用 / 部署单元 | 一个 | **一个** ✅ | 两个 |
| 登录 / 鉴权 | 一套 | **一套** ✅ | 两套（要重建） |
| `users` / `teams` | 台账的 | **共用台账的** ✅ | 画像另建（主数据两份 = 必然漂移） |
| 画像业务数据（30 张 `portrait_*` 表） | 同一个 `.db` | **独立 `portrait.db`** ✅ | 独立 |
| 隐私数据与台账数据是否物理隔离 | ❌ 否 | **✅ 是** | ✅ 是 |
| 画像能否单独备份 / 单独交付 | ❌ 不能 | **✅ 能** | ✅ 能 |
| 台账改表能否碰到画像 | 能（同一文件） | **不能** | 不能 |
| 改造成本 | 零 | **中** | 高 |

**为什么选 B 而不是 C（拆分独立项目）**：C 要额外付出「重建鉴权 + 跨系统接口 + 两套部署」的成本，而画像本来就要读台账的 `users`/`teams`（组长判据 `teams.leader_id`、审批人下拉、家访被访人选择），拆开后这些全变成跨系统调用。**B 已经解决了 90% 的诉求（物理隔离 + 单独交付 + 互不干扰），剩下的收益（"文件夹更整齐"）不值得付这个代价。**

**为什么 `users` / `teams` 要共用**（而不是画像另建一张）：

1. `users` 表里只有 `ehr_id` / `name` / `department` / `team_id` / 账号密码这些**组织与账号信息**，**没有任何隐私数据**——政治面貌、家庭信息、联系方式全在 `portrait_*` 表里。共用不产生隐私外泄。
2. **EHR 号是唯一登录标识**，画像的审批人选择、组长判定、家访被访人全都指向同一批人。两份用户表 = 组员调岗要同步两处 = 必然漂移，而漂移会直接导致"审批人找不到"。
3. 画像已有一张标准的 1:1 扩展表 `portrait_user_metadata`（`user_id` 复用 `users.id`）——**这就是正确的分层模式：账号/组织共用，画像业务字段自己扩展**。
4. 画像另建用户表还得解决跨系统 `user_id` 映射，纯粹是给自己加故障点。

**要付出的代价（必须正视）**：

| 代价 | 说明 |
|---|---|
| **跨库事务** | 员工点提交 → 画像写 `portrait.db`，引擎写 `workflows`（在 `taizhang.db`）。两边**不在同一个事务**里，引擎成功而画像状态更新失败时会出现不一致。形态 A 没这个问题。 |
| ~~4 张 Workflow 表的归属必须定~~ | ✅ **已定（2026-10-21）：4 张 Workflow 表全部搬进 `portrait.db`。** 画像自带审批引擎，跨库事务问题最小化。台账的审批流仍走原表（台账侧不动）。 |

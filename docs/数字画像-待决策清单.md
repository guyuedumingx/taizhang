### 决策 1 · 组长以什么标识为准？→ **A：启用 `teams.leader_id`**

**要解决什么**：代码里"组长 ≡ `users.team_id` 非空"——**任何员工只要被分了个组，就自动获得组长权限**（能看本组所有人档案、能建家访、能审批）。这是审计报告 §1.1 里 8 项功能权限过宽的共同根因。

**已存在的字段**：`teams.leader_id`（`app/models/team.py:15`，`ForeignKey("users.id")`），建表时就有，**代码里一次都没用过**，当前全是 NULL。

**做法**：
- 组长判据从 `viewer.team_id is not None` 改成 `viewer.id == team.leader_id`
- 组表里的 `leader_id` 指向本组的某个人；谁被指向谁是组长
- 一组一个组长，组长身份跟着他所在的组走

##### 怎么判断台账域那 8 处该不该跟着改（2026-10-21 补充判断方法）

先分清**两套语义**的差别，这是判断的前提：

| | 画像的「组长」 | 台账的「同组」 |
|---|---|---|
| 谁能用 | 组长 1 个人（`teams.leader_id` 指向的那位） | 全组所有人（`team_id` 相同的都算） |
| 业务含义 | 「这个组的负责人」，有管理动作（建家访、审批、看本组全员档案） | 「这份台账属于我们组」，组内成员都能看/提交 |
| 判定式 | `viewer.id == team.leader_id` | `viewer.team_id == record.team_id` |

**判断口诀：这条权限的**受益人**是"一个人"还是"一群人"？**

- 受益人是**一群人**（组内成员共同查看/提交本组数据）→ 保留「同组」语义，**不要**改成组长判据。
  - 台账 8 处基本都属于这一类：台账是"组的台账"，组员都要能录能看。
- 受益人是**一个人**（某个角色专属的管理动作，如"审批人必须是组长"）→ 应统一到 `teams.leader_id`。

**具体到本项目，判断步骤**：

1. 先确认**业务上到底谁该有这个权限**，而不是先看代码怎么写的。问业务方一句："这项操作，组里的所有人都能做，还是只有组长能做？"
2. 若答案是"只有组长" → 换成 `TeamService.is_leader(db, user)`。
3. 若答案是"组里都行" → 保留同组语义，**但要在代码里写清注释**，标明"这是台账的同组语义，不是画像的组长语义"，避免下次又被当成待统一的漏洞。
4. 换判据时注意**存量影响**：台账域现在有 174 人已分组、10 个组的 `leader_id` **全是 NULL**（决策 1 历史数据一节），若贸然把台账域也改成组长判据，**这 174 人会立刻失去台账权限**（且比画像侧更严重——台账是日常主流程）。所以台账域统一判据**必须等组长指定做完之后**再做。

> **结论（当前不动）**：画像域 21 处已全部收口到 `is_leader`；台账域 8 处保持"同组"（业务上正确）；`approvals.py:409-412` 是 500 死代码（不是第三套口径），已单列一节，**已拍板暂不修**。

### 决策 2 · 员工导入模板 + 初始密码 → **A：管理员在 Excel 里逐个填**

**已确定的前提**：画像将来在内网**单独装一套**，不与台账共用数据库；用户由**管理员批量导入**。

**导入模板 4 列**（全部必填）：

| 列 | 说明 |
|---|---|
| EHR 号 | 7 位数字，唯一标识 |
| 姓名 | 与系统已有姓名不一致时整行失败 |
| 组别 | 按组名匹配，匹配不到整行失败 |
| 初始密码 | **管理员自己填**，见下方复杂度规则 |

**初始密码复杂度规则**（三条硬性，缺一不可）：
- 必须含**大写字母**（A-Z）
- 必须含**小写字母**（a-z）
- 必须含**数字**（0-9）
- 必须含**特殊字符**（如 `!@#$%^&*` 等非字母数字）
- **长度 ≥ 8 位**

**校验失败的处理**：不合规**整行失败**，不静默跳过。失败明细里写清楚是哪个人的哪一列不合规。

> **可复用**：首次登录强制改密字段和逻辑**已实现**。注意 2026-10-20 重构 Phase 4 后该标志已从 `portrait_user_metadata` 归位到 **`users.is_first_login`**（`app/models/user.py:18`），读取走 `auth_service.py:18` 的 `_get_is_first_login()`（保留了旧表的 NULL 回落兼容读）。所有导入的用户首登必须改密，不改不放行。

**PRD 需同步**：PRD `:581` 只写了「EHR 必填、姓名/组别必填」，**没有初始密码这一列**，也没有复杂度规则。这条决策要回写进 PRD §16.1。

##### ✅ 决策 2 的遗留冲突：改密入口的密码规则与之相反 → **A：全局统一为「大小写 + 数字 + 特殊字符、≥8 位」**（2026-10-21 已拍板）

##### 这条冲突"到底有什么影响"（2026-10-21 补充说明）

一句话：**今天代码是能跑的，但"画像单独装一套"这句话目前只兑现了一半——业务数据搬了，审批引擎的表没搬。**

拆成三种部署形态看：

| 部署形态 | 会发生什么 | 严重度 |
|---|---|---|
| **本期就与台账共库**（选项 B） | 一切正常。审批实例落在台账 4 张表里，与台账共用一套工作流 | 🟢 无影响 |
| **本期单独部署，但 4 张 Workflow 表也一起搬**（选项 A） | 需要：给 4 张表加 `portrait_` 前缀 + 写数据迁移 + 引擎泛化到支持两套表。工作量最大，但搬完之后画像**彻底独立**，以后台账怎么改都碰不到画像 | 🟡 一次性大工作量 |
| **本期单独部署，但 Workflow 表没搬**（现状的隐患） | 员工**能提交**（提交表是画像自有的），但**管理员点"通过"会 500**——引擎去写 `workflow_instances` 表，画像的库里没有这张表 | 🔴 员工侧功能直接不可用 |

**具体会 500 的位置**：`app/portrait/services/workflow_bridge.py`（画像提交 ↔ 台账引擎的唯一接触点）→ 引擎实例化要写 `workflows` / `workflow_instances` 等 4 张表。

**因此判断标准其实很简单**，按顺序问自己三句：

1. **本期上线时，画像的部署形态是什么？** —— 与台账共库（同一台机器同一个库）→ 本条**不阻塞上线**，按 B 或 C 走即可；独立一套库 → **必须**做 A，否则审批一走就 500。
2. **如果本期共库，那"单独部署"是本期承诺还是远期愿景？** —— 远期愿景 → 选 C（本期共库 + 代码层面隔离好 `workflow_bridge`，搬的时候只改一个模块）；本期承诺 → 选 A。
3. **搬表的成本能否接受？** —— A 的成本是 4 张表改名 + 迁移脚本 + 引擎双表支持，本期时间够就 A，不够就 C（留接口，不返工）。

> ⚠️ 提醒一个容易被忽略的连带项：选 A 时**不只是改表名**。`app/models/workflow.py` 的模型类在**台账和画像两个 schema 之间被共用**（画像的 `workflow_bridge` import 的是台账的模型）。加前缀必须同时解决"同一份模型定义、两套表名"的问题（例如按 `subject_type` 决定表名，或给模型加 `__table_args__` 的 schema 切换），**否则搬一半会炸**。这是 A 比 B/C 贵的主要原因。

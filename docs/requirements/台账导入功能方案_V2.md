## 1. 决策记录(全部 16 项,本次定稿)

### 1.1 v1.0 沿用决策(共 12 项)

| # | 决策点 | 结论 |
|---|--------|------|
| 1 | 数据来源 | **按系统提供的导入模板填写**,格式可控;系统提供「下载导入模板」功能。不做列映射界面 |
| 2 | 使用者 | **管理员/特定权限点** `ledger:import`,低频操作。入口不对普通用户开放(与导出权限同套机制) |
| 3 | 执行模式 | **预校验 + 确认后导入**(两阶段):上传先出校验报告,管理员确认后才落库。validate 与 commit 之间无状态,commit 时服务端重新解析+校验 |
| 4 | 导入后状态 | **导入即生效**:`active` + `approved`。定位是历史数据补录,不走审批流 |
| 5 | 重复处理 | 预校验**检测重复**(库内撞车 + 文件内部互撞),问题行**默认跳过**,不做 UPSERT |
| 6 | 归属(team) | **配置化映射**:模板字段(如「组别」)按配置反查系统实体——配置到 team 按团队名匹配 `teams.name`;匹配失败进问题清单(也可走 commit 请求所选团队兜底,见 §7) |
| 7 | 数据量级 | **同步处理 + 行数上限** `max_rows=2000`;`warn_rows=5000` 仅警告;`max_rows_hard_limit=5000` 直接拒绝。不做异步队列 |
| 8 | 清洗联动 | 预校验时对配置了清洗规则的字段跑 normalizer:可修复行标注「将自动清洗」并预览 raw→clean;不可修复按 invalid_policy 进问题清单。**落库写原始值**,统计时动态清洗(与主方案原则一致) |
| 9 | `name` 来源 | 模板级配置 `name_field`(如「流水号」);缺省找 `data.name`;都没有则用 `import-{template}-{seq}` 生成 |
| 10 | `unique_keys` 默认值 | 模板级配置 `unique_keys`(如 `["流水号"]`);缺省为 `["name"]` |
| 11 | 柜员号字段格式 | EHR 号固定 7 位数字,反查前预校验(长度+数字),失败进 `user_not_found` |
| 12 | 归属字段映射范围 | **仅** `team` / `created_by`,不做 `updated_by`/`role`/`department` 等 |

### 1.2 V2 新增决策(共 4 项,本次确认)

| # | 决策点 | 结论 | 与 v1.0 的差异 |
|---|--------|------|--------------|
| 13 | **active 台账能否撤回** | **不能**。导入后 active 台账不可编辑、不可删除、**不提供撤回批次 endpoint**。导入批次错只能联系超管走数据库脚本回滚 | 🆕 比 v1.0 更严格;v1.0 §8 隐含允许后续增强撤回 |
| 14 | **`created_by` 归属(双写)** | `created_by_id` = 柜员号字段反查 `users.ehr_id` 得到的用户(业务所属);**新增字段** `imported_by_id` = 当前操作者(导入者);反查失败兜底逻辑见 §7 | 🆕 v1.0 决策 #6 只规定 identity_mapping 反查,未区分 created_by 与 imported_by |
| 15 | **「本人看到自己填的、组长看到本组」** | **本次不做**,作为独立任务排期。本次导入沿用现有可见性(列表查询不过滤团队) | 🆕 与导入功能解耦,避免范围蔓延 |
| 16 | **数据库迁移新增字段** | 同意。新增 `imported_by_id` (Integer nullable) + `import_batch_id` (String(40) nullable, indexed)。手工创建的台账这两个字段为 NULL | 🆕 新增数据库迁移 |

## 2. 总体流程

```
管理员(老王)                          后端
  │
  │ ① 选择模板 → 下载导入模板
  ├──────────────────────────→ 按模板 fields + ledger_import_config 动态生成 xlsx(双 Sheet)
  │                             · Sheet 1: 填表说明
  │                             · Sheet 2: 模板(表头+format_hint+示例+select 下拉)
  │ ② 按模板填写 Excel,上传
  ├──────────────────────────→ ③ 预校验(不落库):
  │                             · 表头/必填/类型校验
  │                             · 清洗层试跑(配置了 pipeline 的字段)
  │                             · 归属映射(team/ehr 反查)
  │                             · 重复检测(库内+文件内)
  │ ④ 查看校验报告 ←────────── 返回:可导入 N / 问题 M / 可自动清洗 K + 详细列表
  │ ⑤ 确认导入
  ├──────────────────────────→ ⑥ 重新解析+二次校验,以服务端实时结果为准
  │                             逐行写入(每 200 行 commit 一次):
  │                             · data 写原始值
  │                             · created_by = 柜员号反查用户(失败兜底见 §7)
  │                             · imported_by = 当前操作者(老王)
  │                             · import_batch_id = 本次批次 UUID
  │                             · status=active, approval_status=approved
  │ ⑦ 查看导入结果 ←────────── 成功清单 + 失败清单(可导出 Excel)+ batch_id
```

**设计要点:validate 与 commit 之间无状态**。commit 时重新解析文件、重新执行全部
校验,以服务端当时的校验结果为准——避免「预览后文件被改/数据被他人变更」造成的
不一致,也省去缓存预览结果的存储。

**不可撤回**:导入完成后,本批次台账**无法编辑、无法删除、无法撤回**。如发现整批错误,需联系超管走数据库脚本手动回滚(后续若放开超管撤回,扩展点已预留,见 §8)。

## 3. 数据库迁移(新增 2 字段)

新建迁移脚本,参照 [taizhang-migration-toolkit/migrate_auto_fill_config.py](taizhang-migration-toolkit/migrate_auto_fill_config.py) 的 SQLite/Oracle 兼容模式:

**SQLite**:
```sql
ALTER TABLE ledgers ADD COLUMN imported_by_id INTEGER REFERENCES users(id);
ALTER TABLE ledgers ADD COLUMN import_batch_id VARCHAR(40);
CREATE INDEX ix_ledgers_import_batch_id ON ledgers(import_batch_id);
```

**Oracle**:
```sql
ALTER TABLE ledgers ADD (imported_by_id NUMBER REFERENCES users(id));
ALTER TABLE ledgers ADD (import_batch_id VARCHAR2(40));
CREATE INDEX ix_ledgers_import_batch_id ON ledgers(import_batch_id);
```

**模型侧更新** ([backend/app/models/ledger.py](backend/app/models/ledger.py)):

```python
imported_by_id = Column(Integer, ForeignKey("users.id"), nullable=True)
import_batch_id = Column(String(40), nullable=True, index=True)
imported_by = relationship("User", foreign_keys=[imported_by_id])
```

**Pydantic Schema 同步更新** ([backend/app/schemas/ledger.py](backend/app/schemas/ledger.py)):
- `LedgerBase` 加 `imported_by_id: Optional[int] = None`、`import_batch_id: Optional[str] = None`
- 响应模型 `Ledger` 加 `imported_by_name: Optional[str] = None`

**手工创建的台账**:这两个字段均为 NULL,不影响现有逻辑。

**Ledger.creator 关系保持不变**(仍指向 `created_by_id`),新增的 `imported_by` 是独立关系,不与 `creator` 冲突。

## 4. 导入配置(零数据库改动)

新建 `backend/ledger_import_config.json`(加载器照抄 [auto_fill_trigger_loader.py](backend/app/core/auto_fill_trigger_loader.py) 的「启动加载 + 内存缓存 + reload()」模式),与 [field_normalizers.json](backend/field_normalizers.json) 同范式:

```jsonc
[
  {
    "template_name": "特殊业务台账",
    "max_rows": 2000,                      // 软上限,默认 2000
    "warn_rows": 5000,                     // 警告阈值,默认 5000
    "max_rows_hard_limit": 5000,           // 硬上限,默认 5000;超过直接拒绝
    "name_field": "流水号",                 // 台账 name 取值字段
    "unique_keys": ["流水号"],              // 重复检测键
    "identity_mapping": {                  // 归属映射:字段名 → 系统属性
      "team": "组别",                       // 「组别」字段的值 → 按团队名匹配 teams
      "created_by": "柜员号"                // 「柜员号」字段的值 → 按 ehr_id 匹配 users
    },
    "field_order": ["流水号", "交易码", "金额", "柜员号", "组别", "业务日期", "摘要"]
  }
]
```

| 配置项 | 说明 |
|--------|------|
| `max_rows` | 软上限,超过给警告但允许(默认 2000) |
| `warn_rows` | 警告阈值,超过提示用户拆分(默认 5000) |
| `max_rows_hard_limit` | 硬上限,超过直接 400 拒绝(默认 5000) |
| `name_field` | 台账 `name` 取哪个字段的值;缺省顺序:本字段 → `data.name` → `import-{template}-{seq}` |
| `unique_keys` | 重复检测键,支持多字段组合;缺省为 `["name"]` |
| `identity_mapping.team` | 字段名 → 按 `teams.name` 精确匹配 |
| `identity_mapping.created_by` | 字段名 → 按 `users.ehr_id` 精确匹配;EHR 号校验:7 位数字 |
| `field_order` | 生成导入模板时的列顺序;未列出的模板字段追加在后面 |

**加载器**: `backend/app/core/import_config_loader.py`(照抄 `auto_fill_trigger_loader.py`)
**reload 端点**: 复用现有 `POST /api/v1/auto-fill-configs/reload` 模式,新增 `POST /api/v1/ledgers/import-configs/reload`(需 `template:edit` 权限)

## 5. 导入模板下载

`GET /api/v1/ledgers/import-template/{template_id}` → xlsx 文件流

**结构(双 Sheet)**:

| Sheet | 内容 |
|-------|------|
| Sheet 1: 「填表说明」 | 标题段(导入流程 4 步图)+ 字段填写格式(从 `field.options.format_hint`,无则用 generic 提示)+ 必填标记 |
| Sheet 2: 「{模板名}」 | 第 1 行:表头(按 `field_order`,字段 label);第 2 行:format_hint + 必填标记;第 3 行:示例(灰色斜体,标注「示例,请删除后填写」) |

**关键技术细节**:
- **select 字段**:生成 Excel 数据有效性下拉(从 `Field.options`),从源头杜绝乱填
- **number 字段**:单元格设数值格式(`#,##0.00`)
- **复用**: `services/ledger_service.export_ledger` 的 pandas + openpyxl 设施(BytesIO 流式响应)

**依赖注意**:`Sheet 1` 的 `format_hint` 文案依赖 [特殊栏位方案 2.3.2](docs/requirements/特殊栏位处理与填写格式提示方案.md) 的 options schema 扩展;**未就绪时降级**为固定文案(如「请按字段要求填写」),接口结构不变。

## 6. API 设计

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/v1/ledgers/import-template/{template_id}` | 下载导入模板(双 Sheet xlsx) |
| GET | `/api/v1/ledgers/import-configs` | 列出当前导入配置(供前端显示) |
| POST | `/api/v1/ledgers/import-configs/reload` | 热重载 `ledger_import_config.json` |
| POST | `/api/v1/ledgers/import/validate` | 预校验,不落库。body: `template_id` + `file` + 可选 `team_id`。返回校验报告 |
| POST | `/api/v1/ledgers/import/commit` | 确认导入。body 同 validate;服务端重新校验后逐行写入 |
| GET | `/api/v1/ledgers/import/history` | 导入历史列表(本批次维度) |
| GET | `/api/v1/ledgers/import/history/{batch_id}` | 单批次详情 |
| GET | `/api/v1/ledgers/import/history/{batch_id}/failures` | 单批次失败清单下载 xlsx |

**所有 import/* 端点**:权限校验 `deps.check_permissions("ledger", "import", current_user)`,无权限返回 403。

### 6.1 校验报告结构

```jsonc
{
  "template_id": 1,
  "batch_id": "IMP-20260908-a3f7b2c1",      // 本次校验分配的批次预览号(commit 时可能因二次校验而变化,以 commit 返回的为准)
  "total_rows": 500,
  "importable_count": 462,
  "cleanable_count": 18,
  "issues": [
    { "row": 12, "type": "missing_required", "field": "流水号", "raw": "", "reason": "必填字段为空" },
    { "row": 33, "type": "duplicate", "field": "流水号", "raw": "A001", "reason": "与库内台账 #886 重复" },
    { "row": 47, "type": "team_not_found", "field": "组别", "raw": "城东支行", "reason": "团队不存在" },
    { "row": 58, "type": "user_not_found", "field": "柜员号", "raw": "E9999", "reason": "EHR 号不存在或格式错误" },
    { "row": 60, "type": "uncleanable_value", "field": "金额", "raw": "100-200", "reason": "金额无法解析" },
    { "row": 501, "type": "row_limit_exceeded", "field": null, "raw": null, "reason": "总行数 501 超过 max_rows=500(警告)或 hard_limit=5000(拒绝)" }
  ],
  "cleanable_previews": [
    { "row": 21, "field": "金额", "raw": "人民币叁仟柒佰元整", "clean": 3700 }
```

## 7. 预校验规则(按执行顺序)

```
① 文件级:MIME、表头与模板匹配、行数(超 max_rows 警告、超 max_rows_hard_limit 拒绝)
② 逐行:
   a. 必填检查(模板 required 字段)
   b. 清洗试跑:配置了 pipeline 的字段跑 normalizer
      → 可修复:记入 cleanable_previews,后续校验用 clean 值
      → 不可修复:记入 issues(uncleanable_value)
   c. 类型检查:number/date 字段值类型合法性
   d. EHR 号格式预校验:柜员号字段必须 7 位数字(user_not_found 包含此情况)
   e. 归属映射:
      · team:按 identity_mapping.team 字段值精确匹配 teams.name
        · 失败 → 该行进 issues(team_not_found);若 commit 请求体带 team_id 则用其兜底
        · 兜底优先级:identity_mapping 反查 > commit 请求的 team_id > 不允许导入(拒绝整批)
      · created_by:按柜员号字段值精确匹配 users.ehr_id
        · 失败 → 该行进 issues(user_not_found);commit 时兜底为当前操作者
   f. 重复检测:unique_keys 组合值,查库内 + 文件内已见集合
   g. name 取值:按 name_field 取,缺省 data.name,都没有则用 import-{template}-{seq}
③ 汇总:importable = 总行数 - issues 行数;cleanable 单独计数展示
```

**库内去重的 SQL 方案**(避免 N+1):
- SQLite: `json_extract(data, '$.流水号')` 在 WHERE 中直接用
- Oracle: `JSON_VALUE(data, '$.流水号')`;低版本回退到 `dbms_lob.substr` 字符串匹配
- 实现位置: `crud/ledger.py` 新增 `get_existing_unique_keys(template_id, field_names)` 方法,单次查询返回 `{key_value: ledger_id}` 映射

## 8. 写入逻辑

复用 [ledger_service.create_ledger](backend/app/services/ledger_service.py#L172-L241) 的双写链路(`data JSON ↔ field_values`),**差异字段**:

| 字段 | 取值 |
|------|------|
| `data` | 按模板字段写入行值(**原始值**,清洗值只用于校验,不落库) |
| `name` | 按 name_field 取;缺字段走 `data.name`;都没有则 `import-{template}-{seq}` |
| `status` | `active` |
| `approval_status` | `approved` |
| `submitted_at` / `approved_at` | 导入时刻 |
| `team_id` | identity_mapping 反查结果(若失败,使用 commit 请求所选 `team_id`);**不允许双重兜底都失败**(若反查失败且无请求 team_id,该行进 issues 不导入) |
| `created_by_id` | identity_mapping 反查用户(失败兜底为当前操作者) |
| `updated_by_id` | = `created_by_id` |
| 🆕 `imported_by_id` | 当前操作者(老王),**始终有值** |
| 🆕 `import_batch_id` | 本次 commit 生成的 UUID(例如 `IMP-20260908-a3f7b2c1`) |
| `audit_logs` | 不写入(`AuditLog` 主要服务于审批流,导入不属于审批);追溯通过 `imported_by_id` + `import_batch_id` |
| `system_logs` | 写入一条:`module=ledger, action=import, message="导入批次 {batch_id} 成功 {N} 失败 {M}", user_id=老王, details={"import_batch_id": "...", "template_id": ..., "filename": ..., "success_count": N, "failed_count": M}` |

**写入策略**:每 200 行 `db.commit()` 一次,失败行不阻断后续行。失败原因(数据库异常等)记入 `failed_items`,与二次校验新增失败合并。

**不可编辑/不可删除**:导入完成后,本批次台账**无法编辑、无法删除**。`update_ledger` 和 `delete_ledger` 维持现有逻辑(只允许 draft/returned 状态操作)。**当前不提供撤回批次 endpoint**——若未来放开超管撤回,扩展点已预留(`import_batch_id` 索引 + `imported_by_id` 字段),只需新增 endpoint + 鉴权。

## 13. 风险与降级

| 风险 | 影响 | 降级方案 |
|------|------|----------|
| 清洗层(field_normalizers)未就绪 | 「可自动清洗」预览无法实现 | 降级:所有有清洗配置的字段,清洗失败值统一进 `uncleanable_value` 问题清单;接口结构不变,后续接清洗层时直接受益 |
| Oracle JSON 查询兼容性(同 [特殊台账方案 9.1](docs/requirements/特殊台账统计实现方案.md)) | 库内 `unique_keys` 查询失败 | Oracle 12c+ 用 `JSON_VALUE`;低版本回退到 `dbms_lob.substr` 字符串匹配;实现时按生产 Oracle 版本选择 |
| 2000 行同步处理慢 | 用户等待 | 单文件 2000 行预计 5-15 秒;前端进度条 + `message.loading` 即可;超过 `max_rows_hard_limit` 直接拒绝 |
| 批次错误无法撤回 | 用户后悔成本高 | 当前决策(决策 #13):联系超管走 DB 脚本;预留 `import_batch_id` 索引便于未来加撤回 |
| 现有 list 接口无团队过滤 | 「本人看到自己填的、组长看到本组」不成立 | 当前决策(决策 #15):本次不做;作为独立任务排期 |

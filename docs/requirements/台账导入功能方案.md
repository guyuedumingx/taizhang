## 1. 需求决策记录(grill-me 访谈结论)

| # | 决策点 | 结论 |
|---|--------|------|
| 1 | 数据来源 | **按系统提供的导入模板填写**,格式可控;系统提供「下载导入模板」功能。不做列映射界面 |
| 2 | 使用者 | **管理员/特定权限点**,低频操作。入口不对普通用户开放 |
| 3 | 执行模式 | **预校验 + 确认后导入**(两阶段):上传先出校验报告,管理员确认后才落库 |
| 4 | 导入后状态 | **导入即生效**(active + approved)。定位是历史数据补录,不走审批流 |
| 5 | 重复处理 | 预校验**检测重复**(库内撞车 + 文件内部互撞),问题行**默认跳过**,不做 UPSERT |
| 6 | 团队/用户归属 | **配置化映射**:模板字段(如「柜员号」「组别」)按配置反查系统实体——配置到 team 按团队名匹配,配置到 ehr 按 EHR 号匹配用户。匹配失败进问题清单 |
| 7 | 数据量级 | **同步处理 + 行数上限**(建议 2000 行/文件),超限提示拆分。不做异步队列 |
| 8 | 清洗联动 | 预校验时对配置了清洗规则的字段跑 normalizer:可修复行标注「将自动清洗」并预览 raw→clean;不可修复按 invalid_policy 进问题清单。**落库写原始值**,统计时动态清洗(与主方案原则一致) |

## 2. 总体流程

```
管理员                        后端
  │
  │ ① 选择模板 → 下载导入模板
  ├──────────────────────────→ 按模板 fields 动态生成 xlsx
  │                             (表头=label,第二行=format_hint 示例)
  │ ② 按模板填写 Excel,上传
  ├──────────────────────────→ ③ 预校验(不落库):
  │                             · 表头/必填/类型校验
  │                             · 重复检测(库内+文件内)
  │                             · 归属映射(team/ehr 反查)
  │                             · 清洗层试跑(标注可修复行)
  │ ④ 查看校验报告 ←────────── 返回:可导入 N 条 / 问题 M 条(分类+行号+原因)
  │                             + 可自动清洗 K 条(raw→clean 预览)
  │ ⑤ 确认导入
  ├──────────────────────────→ ⑥ 重新解析+二次校验(以服务端实时结果为准),
  │                             逐行写入,返回导入结果报告
  │ ⑦ 查看导入结果 ←────────── 成功清单 + 失败清单(可导出 Excel)
```

**设计要点:validate 与 commit 之间无状态**。commit 时重新解析文件、重新执行全部
校验,以服务端当时的校验结果为准——避免「预览后文件被改/数据被他人变更」造成的
不一致,也省去缓存预览结果的存储。

## 3. 导入配置(零数据库改动)

新建 `backend/ledger_import_config.json`(加载器照抄 auto_fill/normalizer 的
「启动加载 + 内存缓存 + reload()」模式),与 `field_normalizers.json` 同范式:

```jsonc
[
  {
    "template_name": "特殊业务台账",
    "max_rows": 2000,                      // 行数上限,缺省用全局默认
    "identity_mapping": {                  // 归属映射:字段名 → 系统属性
      "team": "组别",                       // 「组别」字段的值 → 按团队名匹配 teams
      "created_by": "柜员号"                // 「柜员号」字段的值 → 按 ehr_id 匹配 users
    },
    "unique_keys": ["流水号"],              // 业务唯一键字段(重复检测用);缺省检测 name
    "field_order": ["流水号", "交易码", "金额", "柜员号", "组别", "日期"]  // 导入模板列序
  }
]
```

| 配置项 | 说明 |
|--------|------|
| `identity_mapping` | 值只能是 `team` / `created_by`。解析行数据时,取出对应字段的值反查实体:`team` 按团队名称精确匹配;`created_by` 按 `users.ehr_id` 精确匹配。匹配失败 → 该行进问题清单,不导入 |
| `unique_keys` | 重复检测键。支持多个字段组合(如流水号+日期)。检测范围:**库内同模板已有台账** + **本文件内部互相重复** |
| `field_order` | 生成导入模板时的列顺序;未列出的模板字段追加在后面 |

**与清洗层配置的关系**:哪些字段在导入时参与清洗试跑,直接复用
`field_normalizers.json` 的既有配置,不重复定义——单一事实来源原则同样适用于导入。

## 4. 导入模板下载

`GET /api/v1/ledgers/import-template/{template_id}` → xlsx 文件流

| 行 | 内容 |
|----|------|
| 第 1 行 | 表头 = 字段 label(按 `field_order` 排列) |
| 第 2 行 | 格式说明 = 字段的 `format_hint`(来自 options 配置,联动功能 A) + 必填标记,如 `必填;请填纯数字,最多两位小数` |
| 第 3 行 | 示例行(灰色斜体,标注「示例,请删除后填写」) |

- 下拉选项:select 类型字段生成 Excel 数据有效性下拉(从 `Field.options` 数组),
  从源头杜绝乱填;
- number 字段单元格设数值格式提示;
- 该接口复用现有 `export_ledger` 的 pandas + openpyxl 设施。

## 5. API 设计

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/v1/ledgers/import-template/{template_id}` | 下载导入模板 |
| POST | `/api/v1/ledgers/import/validate` | 预校验,不落库。body: `template_id` + file。返回校验报告 |
| POST | `/api/v1/ledgers/import/commit` | 确认导入。body 同上;服务端重新校验后逐行写入 |

**校验报告结构**:

```jsonc
{
  "template_id": 1,
  "total_rows": 500,
  "importable_count": 462,
  "cleanable_count": 18,          // 其中 18 条有乱填但可自动修复
  "issues": [                      // 问题行,按类型分组
    { "row": 12, "type": "missing_required", "field": "流水号", "raw": "", "reason": "必填字段为空" },
    { "row": 33, "type": "duplicate", "field": "流水号", "raw": "A001", "reason": "与库内台账 #886 重复" },
    { "row": 47, "type": "team_not_found", "field": "组别", "raw": "城东支行", "reason": "团队不存在" },
    { "row": 58, "type": "user_not_found", "field": "柜员号", "raw": "E9999", "reason": "EHR 号不存在" },
    { "row": 60, "type": "uncleanable_value", "field": "金额", "raw": "100-200", "reason": "金额无法解析" }
  ],
  "cleanable_previews": [          // 可自动清洗行预览
    { "row": 21, "field": "金额", "raw": "人民币叁仟柒佰元整", "clean": "3700" }
  ]
}
```

问题类型枚举:`missing_required` / `duplicate` / `team_not_found` /
`user_not_found` / `uncleanable_value` / `type_mismatch` / `row_limit_exceeded`。

**导入结果报告**(commit 响应):成功数、失败数、失败清单(同 issues 结构,
可导出 Excel——复用统计模块的导出设施)。

## 6. 预校验规则(按执行顺序)

```
① 文件级:格式(xlsx/csv)、表头与模板匹配、行数上限(max_rows)
② 逐行:
   a. 必填检查(模板 required 字段)
   b. 清洗试跑:配置了 pipeline 的字段跑 normalizer
      → 可修复:记入 cleanable_previews,行数据按 clean 值参与后续校验
      → 不可修复:按 invalid_policy,flag 类记入 issues(uncleanable_value)
   c. 类型检查:number/date 字段的值类型合法性
   d. 重复检测:unique_keys 组合值,查库内 + 查文件内已见集合
   e. 归属映射:identity_mapping 各字段反查 team/ehr,失败进 issues
③ 汇总:importable = 总行数 - issues 行数;cleanable 单独计数展示
```

## 7. 写入逻辑

复用现有台账创建链路的数据写入逻辑(保持 `data` JSON 与 `field_values`
表双写一致,与 `create_ledger` 行为对齐),差异点:

| 字段 | 取值 |
|------|------|
| `data` | 按模板字段写入行值(**原始值**,清洗值只用于校验,不落库) |
| `status` | `active`(导入即生效) |
| `approval_status` | `approved` |
| `submitted_at` / `approved_at` | 导入时刻 |
| `team_id` | identity_mapping 反查结果;未配置 team 映射时用导入界面所选团队 |
| `created_by_id` / `updated_by_id` | identity_mapping 反查用户;反查不到兜底当前操作者 |
| `audit_logs` | 记录导入批次(操作者、文件名、成功/失败数),可追溯 |
| `name` | 取模板「名称」类字段值;若模板无此约定,用 `流水号` 或行序生成 |

写入按批次 commit(如每 200 行一次),失败行不阻断后续行。

## 8. 权限与入口

- 新增权限点 `ledger:import`(后端 `deps.check_permissions` 校验,前端
  `config.ts` 常量),仅授予管理员角色;
- 入口:台账列表页(或模板详情页)「导入」按钮,无权限不渲染;
- 导入产生的台账对普通用户完全等同手工创建的台账,无特殊标记
  (溯源靠 audit_logs)。

## 9. 实现步骤

| 步骤 | 内容 | 依赖 |
|------|------|------|
| Step 1 | `ledger_import_config.json` + loader(照抄 auto_fill 模式) | 无 |
| Step 2 | 模板下载接口(动态表头 + format_hint + select 下拉) | Step 1 |
| Step 3 | 预校验服务(校验规则 ①②③ + 清洗试跑) | Step 1,依赖清洗层 Step 0 |
| Step 4 | commit 接口(二次校验 + 批量写入 + audit log) | Step 3 |
| Step 5 | 前端导入向导(上传 → 报告 → 确认 → 结果) | Step 2~4 |
| Step 6 | 失败清单导出 Excel | 复用统计导出设施 |

**前置依赖:清洗层(特殊栏位方案 Step 0)必须先行**——预校验的清洗试跑
和「可自动修复」标注都建立在其之上。若清洗层未就绪,导入可先降级为
「乱填值一律进问题清单」,后续再接清洗层,接口结构不变。

---

## 1. 背景与目标

统计分析功能依赖台账数据质量。当前某类台账模板的「金额」栏位存在大量乱填
(如 `100万`、`¥1,234.56`、`约5000`、`无` 等),导致金额求和/筛选不可用。

本方案覆盖两端:

| 功能 | 解决什么 | 时机 |
|------|---------|------|
| **A. 填写格式提示** | 引导用户正确填写,减少新增脏数据 | 录入时(治本) |
| **B. 字段值清洗层** | 统计时归一化存量脏数据,保证统计准确 | 查询/统计时(兜底) |

**硬约束:不改数据库结构**(不加表、不加列、不做数据迁移)。

---

## 2. 功能 A:填写格式提示(零迁移方案)

### 2.1 目标效果

台账表单中,金额栏位下方/输入框内显示建议格式:

```
金额:  [ 例如: 12345.67          ]
        ⓘ 请填纯数字,最多两位小数,单位:元
```

### 2.2 方案对比

| 方案 | 改数据库? | 优点 | 缺点 | 结论 |
|------|----------|------|------|------|
| A1. 新建字段扩展表 | ❌ 是 | 结构清晰 | 违反约束,需迁移(Oracle 生产) | 排除 |
| **A2. 复用 `Field.options` JSON 列** | ❌ 否 | 零迁移;配置随字段走(复制模板自动带上);模板管理界面可直接编辑 | options 语义扩展需约定 | **✅ 推荐** |
| A3. 前端/后端 JSON 配置文件(参照 auto_fill_triggers.json) | ❌ 否 | 完全不动后端 | 按「字段名」匹配,改名即漂移;改文案要发版 | 仅作全局默认值的补充 |

### 2.3 推荐方案(A2)详细设计

#### 2.3.1 现状

- `fields.options` 列为 JSON 类型,当前仅 `select` 字段使用,存字符串数组。
- API 层 `backend/app/schemas/field.py:12` 将其收窄为 `Optional[List[str]]`。
- 前端 `LedgerForm.tsx` 按 `field.type` 分支渲染,已有 placeholder 机制
  (auto-fill 加载时占用,加载完成后空闲)。

#### 2.3.2 options 结构约定

利用 JSON 列的天然扩展性,按字段类型区分结构:

```jsonc
// select 字段:保持现状(数组)
"options": ["选项A", "选项B"]

// input / textarea / number 字段:扩展为对象
"options": {
  "placeholder": "例如: 12345.67",          // 输入框内灰字
  "format_hint": "请填纯数字,最多两位小数,单位:元",  // 字段下方说明文字
  "format_tooltip": "不支持'万'、'约'等修饰词"   // label 旁 ⓘ 图标的 Tooltip(可选)
}
```

前端渲染时按 `Array.isArray(options)` 区分,两者互不干扰。

#### 2.3.3 需要的改动(均为代码,零数据库迁移)

| 层 | 文件 | 改动 |
|----|------|------|
| API Schema | `backend/app/schemas/field.py` | `options` 类型放宽为 `Optional[Union[List[str], dict]]`(一行) |
| 前端类型 | `frontend/src/types.ts` | `Field.options` 类型同步放宽 |
| 模板管理页 | `TemplateForm.tsx` / `TemplateDetail.tsx` 字段编辑区 | 非输入型字段增加「填写提示」「格式说明」两个输入框,写入 options 对象 |
| 台账表单 | `LedgerForm.tsx` | 渲染时读取 options:数组→select 选项;对象→placeholder / format_hint / Tooltip |

#### 2.3.4 前端交互设计

- `input` / `textarea` / `number`:Input 的 `placeholder` 显示「例如: xxx」;
  字段下方以次要文字显示 `format_hint`;label 旁可选 ⓘ Tooltip 显示 `format_tooltip`。
- 与 auto-fill 的 placeholder 冲突处理:auto-fill 加载中优先显示「正在查询...」,
  加载完成或失败后回落到 `options.placeholder`。
- `date` / `select`:依赖组件自身交互,不展示格式提示。

## 3. 功能 B:字段值清洗层(统计时归一化)

### 3.1 乱填模式清单(按可预见频率排序)

| 模式 | 示例 | 清洗策略 |
|------|------|---------|
| 千分位/货币符/空格 | `1,234,567`、`¥1000`、` 500 ` | 删除字符 |
| 单位词 | `100万`、`3千`、`1.5k` | 乘数换算 |
| 修饰词 | `约5000`、`5000左右` | 提取数字 |
| 语义空值 | `无`、`没有`、`0元` | 按 0 计或排除(可配置) |
| 全角/格式错 | `１２３`、`(500)` | 转换 / 识别负数 |
| 多值/范围 | `100-200`、`500或600` | 不可修 → 可疑清单 |
| 大写金额 | `人民币叁仟柒佰元整`、`壹万贰仟叁佰肆拾伍元陆角柒分` | 中文大写金额解析(见 3.2.4) |

### 3.1.1 大写金额清洗方法

中文大写金额有一套完备的文法,可以**无损解析**(不是启发式猜数,是确定性转换):

**支持的要素**

| 要素 | 字符集 | 说明 |
|------|--------|------|
| 前缀 | `人民币` / `RMB` / `￥` / `¥` | 剥离,不参与计算 |
| 数字字 | `零(〇) 壹(一) 贰(二) 叁(三) 肆(四) 伍(五) 陆(六) 柒(七) 捌(八) 玖(九)` | 大写为主,简体小写可配置容忍 |
| 位权字 | `拾(10) 佰(百,100) 仟(千,1000)` | 段内累乘 |
| 节权字 | `万(1e4) 亿(1e8)` | 分段,如 `壹亿贰仟万` |
| 货币单位 | `元(圆/块) 角 分` | 元为整数部分,角=0.1、分=0.01 |
| 结尾字 | `整 / 正` | 表示无角分 |

**省略与占位规则**(解析器必须处理的边界):

| 写法 | 解析值 | 规则 |
|------|--------|------|
| `拾伍元` | 15 | 「拾」开头隐含 1×10(仅 10~19 区间) |
| `壹佰零伍元` | 105 | 「零」作占位,后面的位权直接加 |
| `壹佰伍拾元` | 150 | 省略「零」时按位权补齐 |
| `壹亿零贰拾万` | 100200000 | 节中间的「零」跳过空段 |
| `柒角伍分` | 0.75 | 无「元」的纯小数金额 |

**解析算法**(分段累加,伪码):

```
result = 0; section = 0; digit = 0
for 字 in 串:
    数字字 → digit = 对应值
    位权字 → section += (digit or 1) × 位权; digit = 0
    节权字 → result += (section + digit) × 节权; section = digit = 0
    元     → result += section + digit; 整数部分结束
    角/分  → 小数部分按 0.1/0.01 累加
    整/正  → 结束
```

**在规则链中的位置**:`uppercase_amount` 放在 `remove_currency` 之前、
`strip_whitespace` 之后。解析失败(非法组合如 `壹拾亿亿`)不猜数,
交由 `invalid_policy`(默认 flag 进可疑清单)。
### 3.2 可扩展清洗器架构(注册表 + 流水线编排)

**设计原则:清洗规则 = 插件;特殊栏位 = 配置。内置规则开箱即用,新规则按约定
实现即可接入,配置文件只负责「哪个栏位、走哪条规则链」,引擎本身永不需要改。**

#### 3.2.1 目录结构与三层模型

```
backend/app/services/normalizers/
  __init__.py            # 导出 register / get_normalizer / run_pipeline
  base.py                # BaseNormalizer 基类 + NormalizeResult
  registry.py            # 注册表: type字符串 → 规则类(装饰器注册)
  loader.py              # field_normalizers.json 加载(缓存 + reload 热更新)
  builtin/               # 内置规则库,每个文件一个规则
    strip_whitespace.py
    fullwidth_to_half.py
    remove_currency.py
    remove_thousands.py
    extract_number.py
    unit_multiplier.py
    uppercase_amount.py   # 大写金额解析(见 3.1.1)
    semantic_null.py      # 无/没有 → fallback
    range_check.py
    invalid_policy.py
```

| 层 | 职责 | 扩展方式 |
|----|------|---------|
| **规则(插件)** | 单一职责:输入 NormalizeResult,输出 NormalizeResult | 新建文件 + `@register`,即插即用 |
| **配置(编排)** | 特殊栏位清单 + 每个栏位的规则链及参数 | 改 JSON 文件,重启或 reload 生效 |
| **引擎** | 按配置顺序执行规则链,收集质量数据 | **永不改动** |

#### 3.2.2 核心约定(后续开发的接入契约)

```python
# base.py —— 每条值在流水线中的状态载体
@dataclass
class NormalizeResult:
    raw: str                    # 原始值,永不被改写(审计/可疑清单用)
    value: Any                  # 当前清洗值,逐规则传递
    is_numeric: bool = False    # 是否已成功转为数值
    is_suspicious: bool = False # 是否判定为可疑
    note: str = ""              # 清洗轨迹,如 "大写金额:叁仟柒佰→3700"

# 规则实现契约
class BaseNormalizer:
    type_name: str                          # 注册名 = 配置里的 "type"
    def __init__(self, params: dict): ...   # 接收配置参数(symbols/mapping 等)
    def apply(self, r: NormalizeResult) -> NormalizeResult: ...
```

```python
# builtin/uppercase_amount.py —— 新增规则的全部工作量示意
@register
class UppercaseAmountNormalizer(BaseNormalizer):
    type_name = "uppercase_amount"
    def __init__(self, params): 
        self.allow_lowercase = params.get("allow_lowercase", True)  # 容忍简体"一千二百"
    def apply(self, r): ...   # 按 3.1.1 算法解析,成功→is_numeric=True
```

**后续开发者新增一种清洗方法,只需两步:**
1. `builtin/` 下新建文件,实现 `BaseNormalizer` 子类,标 `@register`;
2. `field_normalizers.json` 对应栏位的 `pipeline` 里加一行
   `{"type": "新type", ...参数}`。

引擎、统计服务、其他配置零改动。规则间通过 NormalizeResult 传递状态,
天然支持任意排列组合与参数复用。

#### 3.2.3 特殊栏位配置(编排层)

新建 `backend/field_normalizers.json`(加载器照抄 `auto_fill_trigger_loader.py`
的缓存 + reload 模式):

```jsonc
[
  {
    "template_name": "特殊业务台账",       // 模板名; "*" 表示该模板名下任意匹配字段
    "field_name": "金额",                  // 特殊栏位清单就在这里维护
    "pipeline": [                          // 规则链,顺序敏感,按序执行
      { "type": "strip_whitespace" },
      { "type": "fullwidth_to_half" },
      { "type": "uppercase_amount" },      // 大写金额优先于去货币符
      { "type": "remove_currency", "symbols": ["¥", "￥", "元", "$"] },
      { "type": "remove_thousands" },
      { "type": "extract_number" },
      { "type": "unit_multiplier", "mapping": { "万": 10000, "千": 1000, "k": 1000 } },
      { "type": "range_check", "min": 0, "max": 100000000, "out_of_range": "flag" }
    ],
    "invalid_policy": { "action": "flag", "fallback": null }  // 链尾兜底
  }
]
```

配置即清单:哪些栏位算「特殊栏位」、各自怎么洗、洗不动怎么办,全部由这份文件
声明,不需要在任何代码里硬编码字段名。

#### 3.2.4 链尾兜底策略(invalid_policy)

`invalid_policy` 作为规则链的收尾动作,决定「整条链跑完仍未得到数值」时的处置:

| action | 行为 | 适用 |
|--------|------|------|
| `flag` | 修不出的值不参与聚合,计入可疑清单 | **推荐默认** |
| `fallback` | 修不出按 fallback 值计算(如 `无`→0) | 语义空值 |
| `raw` | 原样保留 | 文本型字段 |

### 3.3 统计查询链路

```
查询请求
  ↓ ① SQL 粗筛: template_id / status / team / 时间范围(纯关系列,两库高效)
  ↓ ② 分批取候选行 data JSON
  ↓ ③ Python 清洗层: 按配置归一化 → (raw, clean, is_suspicious)
  ↓ ④ 内存聚合: SUM / COUNT / GROUP BY(用 clean 值)
  ↓ ⑤ 响应 = 统计结果 + 数据质量报告
```

**聚合放 Python 层的理由**:
- Oracle `JSON_VALUE` 上做中文单位换算不现实(SQLite 同理),复杂规则只有应用层能干净实现;
- 顺带规避 Oracle JSON 函数版本兼容风险(实现方案文档 9.1);
- 每个值过清洗函数时顺手分类,`data_quality` 报告几乎免费。

**响应附带质量报告**:

```jsonc
{
  "total_count": 1500,
  "sum_amount": 34567890.50,
  "cleaned_count": 87,
  "suspicious_count": 12,
  "suspicious_items": [
    { "ledger_id": 886, "field": "金额", "raw": "100-200", "reason": "多值/范围,无法确定" }
  ]
}
```

python clean_field_values.py --template 特殊业务台账 --field 金额 --dry-run  # 只预览"原值→清洗值"对照

### 3.5 `field_filters` 金额筛选联动

## 4. 两功能的联动:单一事实来源

**格式规则只定义一次,派生三个消费方**,避免「提示说可以填万、清洗却把万 flag 掉」的矛盾:

```
                    ┌──────────────────────────────┐
                    │  field_normalizers.json      │
                    │  (格式规则的唯一定义处)        │
                    └──────────┬───────────────────┘
                               │ 派生
          ┌────────────────────┼────────────────────┐
          ▼                    ▼                    ▼
   录入校验(前端/后端)    填写格式提示          统计清洗(后端)
   保存时按规则校验       placeholder/说明文案    归一化 + 可疑清单
```

- 后端新增一个轻量接口(如 `GET /api/v1/templates/{id}/field-format-hints`),
  从 normalizers 配置派生各字段的 `placeholder` / `format_hint` 文案;
- 模板管理界面手动在 options 里填的提示**优先级更高**(显式配置覆盖派生默认值);
- 若后续做录入强校验,校验规则同样从配置派生。

## 5. 实现顺序建议

| 步骤 | 内容 | 依赖 |
|------|------|------|
| Step 0 | field_normalizers 配置体系 + 清洗服务(纯后端) | 无 |
| Step 1 | options schema 放宽 + 模板管理页提示编辑 + 表单提示渲染 | 无 |
| Step 2 | 统计查询服务(内嵌清洗层)+ 质量报告 | Step 0 |
| Step 3 | Excel 导出(导出值用清洗后值,附可疑清单 Sheet) | Step 2 |
| Step 4 | 存量修复 CLI(dry-run/apply) | Step 0 |
| Step 5 | (可选)录入强校验,规则从配置派生 | Step 0/1 |

Step 0 与 Step 1 相互独立,可并行。

## 6. 待确认事项

1. **生产环境乱填样本**:建议导出一批金额字段真实值,按实际频率确定清洗规则优先级,避免做无用规则。
2. **清洗后值是否回写 `data`**:本方案默认统计时动态清洗、不动原始数据;回写仅作为可选治理工具(3.4)。数据量超 10 万行时再考虑清洗结果快照表。
3. **「特殊业务台账」范围**:全部台账还是特定模板?决定清洗配置按模板维度还是全局维度。
4. **提示文案维护者**:格式提示由管理员在模板管理界面维护(A2),还是由开发统一在配置文件维护(A3)?本方案默认前者。
5. **录入校验强度**:仅提示(本方案默认),还是保存时硬校验拦截?
